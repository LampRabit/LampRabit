# Decisions: Projects, templates and the Sites page

The user's decisions and the reasons behind them. Don't reverse one without asking the user; when the user changes one, edit it here with the date.

- **Project templates** (2026-10-30, the user's choices): YAML (`serde_yaml_ng`), built-ins in `src-tauri/templates/` (embedded with `include_str!`, all checked by a test), user ones in `<root>/templates/` (kept on uninstall; a user template with a built-in's id replaces it). `templates.rs` parses and checks them at load (schema, ids, unknown placeholders, conditions), `projects.rs::build` runs the steps. File steps stay inside the project (`templates::inside`). Built-ins run without asking; a user template's risky steps (`RISKY` patterns, unchecked downloads) need approval in the wizard, and the backend refuses them without `approveRisky`. Document new step kinds or placeholders in docs/templates.md.
- **Project serving** (2026-10-31, the user's choices): nobody types a serve command. `sites::Language` (php, node, static; Go/Python later) and `ServeMode` (dynamic, static) come from the files: PHP projects are served by PHP even with a package.json (its dev script runs as an unrouted asset server); Node projects with a dev/start script or server file are dynamic. The command comes from the template's `serve:` section or `apps::suggest`. Routing follows live ports (`ports.rs`, 2026-10-31): `watch_ports` (every 3 s, or when an app's state changes) finds listening sockets natively (Windows TCP table, Linux /proc, lsof on macOS), assigns them to projects by the process's working folder, and routes each domain with `ports::choose` (Files choice → pinned `route_port` → LampRabit's app → lowest port; PHP projects only to a pinned port), dropping a route only after two scans. Routes live in `ports` statics that `sites::scan` reads; a change restarts that site's web server and emits `routes-changed` with notes for toasts. `prepare_app` only picks the port and starts the web server. The "not running" page covers the seconds before the switch back to files. A project's dev server never starts with services, Start all or profiles; a stack profile starts only the project processes it lists (`StackProfile.processes`, "project/process", 2026-11-05). The Sites Overview shows `project_facts` (`facts.rs`: package, framework version, requirements, dependencies installed, whitelisted .env keys, git state with credentials stripped from remotes).
- **Sites page, Commands and processes** (2026-11-05, the user's choices): Overview, Commands, Domains, Settings tabs inside the project card. Processes live in the Commands tab (no Processes tab), edited in a dialog; a process starts by hand, with the project, when LampRabit starts (`at_launch`) or on a crontab `schedule` (`cron.rs`, checked once a minute while the app runs). Command runs are kept in `logs/apps/<project>.runs.json`; crashes send `process-crashed` (a toast with the last lines). Per-site php.ini (`SiteSettings.php_ini`, `xdebug`) is a `[PATH=<project>]` section at the end of php.ini, which php-cgi and php-fpm apply per folder (not FrankenPHP or the CLI). Delete moves a project to the Recycle Bin (`trash` crate). A project's subdomains are served as copies named `project › host`; `list_sites` leaves them out (`sites::is_extra`).
- **lamprabit.toml** (2026-11-05): a project's setup in its folder (`projectfile.rs`), saved from and applied in its Settings, never applied on its own (processes are commands from the repository); applying goes through the normal commands and their checks.
- **Template editor** (`TemplateEditor.tsx`, 2026-11-13, the user's choice: every language, not PHP only): the guided form and its YAML live in `lib/templateYaml.ts`. `templateYaml.test.ts` keeps samples in `src/lib/__fixtures__/templates/` (`UPDATE_TEMPLATE_SAMPLES=1` rewrites them) and `templates::tests::editor_samples_are_valid` parses them with the backend's checks, so a form that writes an invalid template fails a test. A new form option gets a sample.
- **Importing from other tools** (`imports.rs`, 2026-11-13): finds Laragon (laragon.ini's `WWW_Dir`), XAMPP, AMPPS, MAMP, Herd and Valet (config.json `paths` and `Sites/` links), FlyEnv (`host.json` roots), EnvKit (guessed folders: it documents none), WampServer, ServBay and Local by their usual folders, plus any folder the user picks. Projects are copied (never moved or linked: deleting one in LampRabit must not touch the original) through `tmp/import-<name>` and renamed into `www/`; `vendor`/`node_modules` with their manifest and links (Laravel's `public/storage`) are skipped, and the doctor offers to restore them. Databases stay in the other tool: their names are listed with how to export them.
- **Dependencies tab** (`deps.rs`, 2026-11-14): each package manager's dependencies are read from the project's files, never by running the tool; only Check for updates runs Composer/npm/pnpm (`outdated` JSON) or asks registries. Every change goes `dependency_plan` (shown in a dialog) → `run_dependency_action` (re-planned, then `apps.run_command`), so nothing runs unconfirmed and output lands in the project's log. Package names and versions go into a command line: `deps::checked` allows only package-name characters (no spaces, quotes, `<>`, leading `-`). Bun, Deno, uv and conda are runtimes; pnpm and Yarn come from corepack (Node card), else `npx -y`.
- **Package managers when creating a project** (the user, 2026-11-24): Node templates already offered npm, pnpm, Yarn and Bun (`{{pm.*}}`); the same choice now applies to other templates' Node steps (Laravel's frontend build, `TemplateInfo.node_steps`). Python templates offer **pip** (venv + requirements.txt, the default), **uv** (`uv init --bare` + `uv add`: pyproject.toml and uv.lock, no requirements.txt) or **conda** (`conda create --prefix .venv`, packages with its pip) through `{{py}}`, `{{py.venv}}`, `{{py.add}}` and a matching `{{venv.python}}` (`projects::python_values`; conda's Python is `.venv\python.exe` on Windows). Java: Spring Boot on Gradle is its own template (`spring-boot-gradle.yaml`, `{{gradlew}}`), since a template has one serve command. Go, Rust and PHP have one standard tool each.
- **Laravel's dev server** (the user, 2026-11-25): `composer run dev` (Laravel 11+, when composer.json has `dev`) or `php artisan serve` is a Laravel project's default dev server command, on LampRabit's port through `SERVER_PORT`; the domain stays on the web server. Start dev server is a split button whose menu lists the ready-made commands (`apps::serve_commands`, also package.json's dev scripts) and links to the project's settings. Saved commands aren't rewritten.
- **Templates offer what their own installers ask** (the user, 2026-11-25: "expand the project templates"): Laravel's starter kit and Pest, Symfony web app or skeleton, Django REST framework, Flask-SQLAlchemy, Spring Initializr dependencies, on top of the existing Next.js/Vite/Astro choices and the Node/Python package managers. Add a template's choices as `variables:` with `if: vars.x == y` steps (conditions have no `&&`).
- **Git** (the user, 2026-11-25): pull from / push to any remote branch (⋯ next to Pull and Push), and a Tags view (create on any commit/branch, which are on the remote, push one or all, delete here or on the remote, fetch, branch from a tag).
- **Linked projects** (2026-11-21, the user's choice): a developer can link a project folder from anywhere (another drive, a removable disk, a folder they moved for technical reasons) and it gets **every** feature a `www/` project has. Linking never copies or moves the folder, and removing a linked project only unregisters it, never deletes files (imports still copy, as decided). Plan: `.ai/plans/backlog/projects-anywhere.md`.
- **New Project installs what's missing** (the user, 2026-11-26: "if a dependency is missing, auto-install it instead"): Create no longer blocks on a missing PHP, Node.js, language, uv/Conda/Bun or database server. `lib/projectNeeds.ts` works out the list; Create resolves it with `project_requirements` (the same resolver as Services' needs) and installs each as a visible step before the project is made. PHP: with none installed the new one becomes the default; when the default is too old, a fitting version is installed (or an installed one picked) for this project only. Node.js installs NVM first when it's missing. The database is the default server when the template can use it, else its first engine (never SQLite). CLI/MCP project creation still asks to install first (follow-up).
