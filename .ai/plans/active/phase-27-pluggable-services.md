# Phase 27: pluggable services (branch `dev-1.0`)

Status: **in progress**. Listed in the [roadmap](../roadmap.md).

Decided 2026-11-15 (the user's choices): every service is a YAML manifest (format in [docs/services.md](../../../docs/services.md)); community services come from a **LampRabit/Services** repository (a PR per `service.yaml`, reviewed and merged by the user), listed in an in-app marketplace and on the website. Manifests find new software versions themselves, so a software release needs no registry change and a manifest revision is only for changes to how a service is installed or run. **All** built-in services move to manifests; what can't be declarative stays behind named `builtin` hooks only built-in manifests may use. The user is the only signer of the registry's index. "Tools and plugins" (extensions, like a browser's) are a separate later phase, not services.

- **A. Engine: done (2026-11-15).** `manifest.rs` (types, strict parsing, checks: paths stay inside the service's folders, programs inside the install, no shell, ports above 1023 and exactly one health check for community manifests; placeholders with OS separators and `|slash`; `on:` platform values; generic GitHub catalog with a mandatory digest) and 24 manifests in `src-tauri/services/`. Labels, logs, ports, health checks, heavy/slow, config paths, connection details (`ServiceInfo.connection`, replacing `connections.ts`'s table), `.test` domains for web UIs and the Services page catalog all come from the manifests. The 15 declarative services (Mailpit, Redis, Memcached, Meilisearch, Typesense, RustFS, MinIO, Ollama, MongoDB, ClickHouse, Neo4j, Elasticsearch, OpenSearch, RabbitMQ, n8n) and MariaDB/MySQL's command lines launch from YAML; their hand-written launch arms and `configs::write_*` writers are gone, after golden tests showed identical command lines and config files on Windows and Linux. Mailpit, Meilisearch, RustFS and Ollama's catalogs come from their manifest's `source.github`.
- **B1. Downloads from YAML: done (2026-11-15).** `source` gained version strategies (`latest`, `newest`, `per-major`, `per-line`, `newest-tag`), tag suffixes with labels, vendor `url`s with published `sha256`/`sha512` files, `npm` (checked against `dist.integrity`), `lamprabit` (LampRabit's CI builds) and a per-platform list. 17 of 24 services download from their manifest; the hand-written catalogs of Caddy, FrankenPHP, ClickHouse, PostgreSQL, RabbitMQ, Redis (Windows), Neo4j, Elasticsearch, OpenSearch, Typesense and n8n are gone, as are the own-builds branches of Apache, Nginx, Redis, Memcached and MinIO. A release without a checksum is left out (one old redis-windows release has none). `runtimes::tests::live_manifest_catalogs` (ignored; run with `--ignored`) checks every source against the real APIs; it passed on Windows and Linux. Left on `builtin`: MariaDB, MySQL, MongoDB, Tomcat, pgAdmin and Apache/Nginx on Windows (page scraping and vendor APIs).
- **B2. Settings in manifests: done (2026-11-15, the user's request).** `settings:` declares options (`text`, `number`, `toggle`, `choice`) shown in the service's Settings card on the Services page; values are checked against their type, stored in `Settings.service_options` (only those changed from the default), used as `{{setting.<name>}}` and `if: setting.<name>`, and a running service restarts on Apply. Memcached (memory), Redis (append-only), Mailpit (messages kept), Elasticsearch and OpenSearch (heap) use it.
- **B3. Services without an enum variant: done (2026-11-21).** `ServiceKind::Plugin(u16)` and `Runtime::Plugin(u16)` index `manifest::extras()` (append-only, filled by `manifest::register`, which refuses an id that exists already or builtin hooks); both enums serialise as their id, so `Release.runtime`, profiles and the frontend use ids. `Runtime::BUILT_IN` is the fixed list, `Runtime::all()`/`ServiceKind::all()` add the extras. Install-complete marker from the manifest's `binary`; `dependents`, tool domains (`sites::tools`) and `is_tool` include extras. Ports of non-built-in services live in `Ports.extra` (`<id>.<port>`), picked clear of every other service and free on install (`Manifest::assign_ports`), edited on the service's Settings card from the catalog's `RuntimeInfo.ports`; the Services page puts extras in their manifest's category. Frontend `ServiceKind`/`Runtime`/`LogService` accept any id. Tested: `services::tests::a_manifest_only_service_*`, `ServiceSettings.test.tsx`. Left: built-in services' port fields still come from `settingsFields.portFields` (they carry hints and OS rules), and nothing calls `register` outside tests until C. Original plan: `ServiceKind::Plugin(id)` (Copy, an index into the loaded manifests) so a service needs no enum variant; ports of non-built-in services in a `Ports.extra` map (`<id>.<port>`, picked free on install); `Release.runtime` by id; install/remove for manifest-only services; port fields and labels on the Services page from the manifest's `ports` (`settingsFields::portsFor` is still a table).
- **C. Local services: done (2026-11-21).** `manifest::load_local` loads `<root>/services/<id>/service.yaml` at start (a bad file or an id that differs from its folder is skipped and shown as a startup warning); `services` is in `uninstall::KEPT`, so uninstall keeps it and relocate moves it. The registry updates a service in place when its id is added again and hides it on removal (`unregister`), so indexes never move. Commands: `inspect_service_file` (a `manifest::Review`: downloads, checksum, program and args, ports, files, needs), `add_service_file` (refused without `approve`, or while the service runs; copies the file and its icon), `remove_local_service` (refused while running or with versions installed; keeps data). Services page: "Add a service" in the toolbar → `AddServiceDialog` (the review, an unreviewed-file warning) → added and selected; "Remove service" card for local ones (`RuntimeInfo.local`). A plugin's `needs:` feed `catalog::needs`, so the install dialog installs Java/Node first. CLI: `lamprabit service check <file>` (offline review, exit 1 if invalid) and `lamprabit service try <file>` (the smoke test with `--service <file>` in a throwaway folder, its own settings and control file; folder deleted on success). Checked live: `service try` on a Mailpit-based community file installed 1.34.0, ran healthy on 1026 (1025 was busy), stopped. Original plan: `<root>/services/<id>/service.yaml` (kept on uninstall, moved by relocate), "Add a service from a file" on the Services page, unsigned with an approval prompt like user templates' risky steps; `lamprabit service check <file>` and `lamprabit service try <file>` (install and start in a scratch folder) for authors.
- **D. Registry and marketplace.** The LampRabit/Services repo: `services/<id>/{service.yaml,icon.svg,README.md}`, a JSON Schema generated from the Rust types, CI per PR (the app's own `service check`, every platform's asset downloaded and digest-checked, a port clash check against core and registry services, install-start-health-stop smoke tests on Windows, Linux and macOS runners, a loopback-only check), and on merge an `index.json` (id, revision, manifest SHA-256, tier, platforms, category, minimum app version) signed with the user's ed25519 key. The app ships the public key, caches the index like the catalogs, refuses a manifest whose hash isn't in the signed index, and shows a Community section on the Services page (browse, install, update when `revision` changes). Trust tiers: core, official, community, local. The website's marketplace page reads the same index.
- **E. Wider format.** Fewer `builtin` hooks (data-folder initialisation steps, Tomcat's per-project hosts), `kind: tool` (web apps served from files, like Adminer) and `kind: cli` (commands on PATH), backup hooks.

## Additions from the 2026-11-21 spec

[The 2026-11-21 spec](../source-specs/2026-11-21-feature-context.md) ("Feature 5") reaches the same design: declarative, checksums required, built-ins first, a reviewed git registry, consent for unverified manifests. Its suggestion to use TOML is not taken: YAML was decided on 2026-11-15 and is built ([decisions/product.md](../../context/decisions/product.md)). Fields worth adding, mostly to step E:

- `keywords:` synonyms for the command palette ([../backlog/command-palette.md](../backlog/command-palette.md)).
- `config_files:` each with "restart to apply", shown with Open/Reveal/Copy path.
- `backup:` hooks (already in E) feeding existing backups/restore.
- `scope: shared | project`: one install, an instance per project (Firebase emulators, PocketBase; [../backlog/local-baas-payments.md](../backlog/local-baas-payments.md)).
- Per-framework `connection` adapters for service binding ([../backlog/service-binding.md](../backlog/service-binding.md)).
- `docs:` a link to the service's task page.
- A JSON Schema published for editor autocomplete (already planned in D).
